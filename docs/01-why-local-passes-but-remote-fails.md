# 第 1 讲：为什么本地能跑，线上就报错

## 一个真实场景

学生在自己电脑上写完脚本，`node script.js` 一切正常。把同一个文件传到青龙面板，
面板日志里却出现：

```
ReferenceError: fetch is not defined
```

或者：

```
TypeError: AbortSignal.timeout is not a function
```

代码一个字没改，结论却相反。差别只有一个：**运行时的 Node.js 版本**。

## 为什么会这样

JavaScript 语言本身由标准组织维护，但"语言有哪些内置能力"是分两步落地的：

1. 标准里写入某个 API（例如 `fetch`）；
2. 具体运行时（Node.js、浏览器）在某个版本里实现它。

Node.js 的版本很多，而且这些环境往往**不归使用者控制**：

| 环境 | Node 版本谁决定 |
| --- | --- |
| 青龙面板 | 镜像作者，通常停在旧版 |
| 群晖 / NAS | 系统套件，升级要等厂商 |
| OpenWrt / 路由器 | 固件，几乎不可能单独升级 Node |
| Docker 基础镜像 | `FROM node:xx` 的 tag |

开发机是学生自己装的，通常是当前最新版。于是形成一个稳定的错位：

```
开发机：Node 20+   →  全局 fetch 存在，代码通过
运行机：Node 12/14 →  全局 fetch 不存在，代码崩溃
```

这不是"代码写错了"，而是**代码和运行环境不匹配**。排障的关键动作是：
先确认目标环境的版本，再判断代码用到的 API 是否在该版本存在。

## 为什么人工 review 容易漏

- 报错只在运行时出现，静态看不懂；
- 一次提交可能涉及十几个脚本，逐行走查成本高；
- `fetch`、`structuredClone` 这类名字看起来"很基础"，容易被误认为一直都有；
- 本地跑通会给人"已经验证过"的错觉。

所以这件事适合交给工具做：把版本分界线固化成规则，扫描代替肉眼。

## 本讲的检查点

1. 说出你手头目标环境（面板 / NAS / 容器）的 Node 版本；
2. 举出两个"新版本才有"的 API；
3. 解释为什么"本地跑通"不能作为交付依据。
